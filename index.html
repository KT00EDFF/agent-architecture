Start here: workflow vs. agent

Anthropic's taxonomy — the most-cited framing — hangs on one distinction. Get this first; everything else sits inside it.

The foundational split

Anthropic groups everything under “agentic systems” and then splits it in two:

Workflows are “systems where LLMs and tools are orchestrated through predefined code paths.”
Agents are “systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks.” Anthropic, Building Effective Agents (Dec 2024) · quote corroborated

The whole point: an agent (in the strict sense) is defined by dynamic self-direction; a workflow follows predefined code paths. Most “multi-agent” diagrams you see online are actually workflows by this definition — and that's fine. The lesson is to build the simplest thing that works, and only add agent-style autonomy when the task demands it.

Anthropic's building-block patterns

Five workflow patterns plus the autonomous agent. The two the internet most often confuses are routing and orchestrator-workers — pay attention to the line between them.

1 · Prompt chaining

  • Decompose into a fixed sequence of steps; each LLM call processes the previous output.
  • Optional programmatic “gate” checks between steps.

2 · Routing often confused

  • “Classifies an input and directs it to a specialized followup task.”
  • Classify → one specialized path. No fan-out, no synthesis.

3 · Parallelization

  • Sectioning: split into independent subtasks run in parallel.
  • Voting: run the same task several times for diverse outputs.
  • The split here is fixed in code.

4 · Orchestrator-workers the key one

  • “A central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results.”
  • Defining trait: subtasks are NOT pre-defined — the orchestrator decides them at runtime from the input.

5 · Evaluator-optimizer

  • One LLM generates; another evaluates and gives feedback in a loop.

6 · Autonomous agent

  • Fully dynamic: the LLM plans and acts on its own, gaining “ground truth from the environment at each step,” looping to a stop condition.
⚠️
The distinction people get wrong. Parallelization / sectioning = the split is decided in advance, in code. Orchestrator-workers = the split is decided dynamically by the orchestrator from the specific input. That runtime-vs-hardcoded decomposition is the entire difference.
⚠️
Routing ≠ supervising. Routing classifies and sends the request down one path — no synthesis. A supervisor/orchestrator decomposes, fans out to many workers, and synthesizes. AWS actually ships both as separate modes (“supervisor” vs. “supervisor with routing”), which proves they're distinct layers you can combine.

The three roles

Every vendor describes the same hub-and-spoke shape. Here are the roles — with each vendor's real name attached (see the Vocabulary tab for the full map).

Role 1 · the coordinator

Orchestrator / Supervisor / Manager / Lead agent

The decision-maker at the top. It receives the goal, decides how to break it up and who handles each piece, delegates, and synthesizes results into a final answer. It owns the outcome but does little domain work itself.

A supervisor is a central agent that “controls all communication flow and task delegation, making decisions about which agent to invoke based on the current context and task requirements.” LangGraph, langgraph-supervisor · verbatim

Thinks about

  • “How do I decompose this?”
  • “Which worker gets which piece?”
  • “Do I have enough to answer, or spawn more?”

Superpower / risk

  • ✅ Flexible, dynamic decomposition
  • ⚠️ Bottleneck & single point of failure
  • ⚠️ Delegation quality is everything — vague handoffs cause duplicated or missed work
Role 2 · the process

Orchestration — centralized vs. decentralized

“Orchestration” is the flow of agents: which run, in what order, and how the next step is decided. OpenAI names the two philosophies most cleanly:

“There are two main ways to orchestrate agents: 1. Allowing the LLM to make decisions… 2. Orchestrating via code.” OpenAI, Agents SDK — Orchestration · verbatim

Manager pattern (centralized)

  • A central “manager” coordinates specialists through tool calls (agents-as-tools).
  • One agent keeps control and access to the user.

Decentralized pattern (peer)

  • Agents hand off control to a peer that takes over the conversation.
  • Edges are handoffs, not tool calls.
🔀
Handoff ≠ delegation. A handoff (OpenAI / decentralized) transfers control and conversation ownership to a peer that finishes the turn. Delegation (manager / supervisor) keeps the coordinator in control and expects the worker to report back. Different control-flow semantics — don't treat them as the same word.
Role 3 · the specialist

Sub-agent / Worker / Domain agent

The specialist that does the actual work. Narrow scope, given a focused sub-task with just the context it needs, returns a focused result. In Anthropic's research system, the lead agent “spawns subagents to explore different aspects simultaneously” — typically 3–5 in parallel.

✅
Myth to drop: “a sub-agent is just a smaller/weaker agent.” Sub-agent names a role in a hierarchy (delegated-to, scoped, reports up) — not a size class. Anthropic ran subagents on Sonnet and the lead on Opus, but that's an implementation choice, not the definition.

The honest cost/benefit

Multi-agent is not universally better. Anthropic's own numbers:

“Agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats.” Token usage alone “explains 80% of the variance” in performance. Anthropic, How we built our multi-agent research system (Jun 2025) · quote corroborated

When multi-agent wins

  • Heavy parallelization
  • Information exceeding one context window
  • Many complex tools; breadth-first research
  • Their system beat single-agent Opus by 90.2% on an internal research eval

When it doesn't

  • Tightly-coupled tasks like coding (subtasks share state) — mostly stayed single-agent
  • When the task value can't justify ~15× token cost
  • Rule of thumb: start with one agent, add agents only when forced to

Traps this table fixes

❌ “Anthropic calls it a supervisor”

  • They don't. Anthropic says orchestrator (Building Effective Agents) and lead agent (research system). “Supervisor” is LangGraph & AWS vocabulary.

❌ “Handoff is a standard term”

  • OpenAI's handoff = a peer transferring full control. LangGraph uses “handoff” for any transfer, including supervisor→worker. Same word, different scope.

❌ “Orchestration = orchestrator agent”

  • Anthropic uses “orchestrated” even for hardcoded workflows. Workflow orchestration can be pure code; an orchestrator agent decides dynamically.

❌ “Hierarchical is its own thing”

  • LangGraph defines hierarchical = “a supervisor of supervisors” — explicitly a generalization of the supervisor pattern, not a separate species.
