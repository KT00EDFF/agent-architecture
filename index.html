Start here: workflow vs. agent

Anthropic's taxonomy — the most-cited framing — hangs on one distinction. Get this first; everything else sits inside it.

The foundational split

Anthropic groups everything under “agentic systems” and then splits it in two:

Workflows are “systems where LLMs and tools are orchestrated through predefined code paths.”
Agents are “systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks.” Anthropic, Building Effective Agents (Dec 2024) · corroborated

An agent (in the strict sense) is defined by dynamic self-direction; a workflow follows predefined code paths. Most “multi-agent” diagrams online are actually workflows by this definition — and that's fine. The lesson is to build the simplest thing that works, and add autonomy only when the task demands it.

Anthropic's building-block patterns

Five workflow patterns plus the autonomous agent. The two most often confused are routing and orchestrator-workers.

1 · Prompt chaining

  • A fixed sequence of steps; each LLM call processes the previous output.
  • Optional programmatic “gate” checks between steps.

2 · Routing often confused

  • “Classifies an input and directs it to a specialized followup task.”
  • Classify → one path. No fan-out, no synthesis.

3 · Parallelization

  • Sectioning: split into independent subtasks run in parallel.
  • Voting: run the same task several times for diverse outputs.
  • The split is fixed in code.

4 · Orchestrator-workers the key one

  • “A central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results.”
  • Defining trait: subtasks are NOT pre-defined — decided at runtime from the input.

5 · Evaluator-optimizer

  • One LLM generates; another evaluates and gives feedback in a loop.
  • The ancestor of today's fresh-context judge (see The Debate).

6 · Autonomous agent

  • The LLM plans and acts on its own, gaining “ground truth from the environment at each step,” looping to a stop condition.
⚠️
The distinction people get wrong. Parallelization / sectioning = the split is decided in advance, in code. Orchestrator-workers = the split is decided dynamically by the orchestrator from the specific input. That runtime-vs-hardcoded decomposition is the entire difference.
⚠️
Routing ≠ supervising. Routing classifies and sends the request down one path — no synthesis. A coordinator decomposes, fans out, and synthesizes. AWS ships both as separate modes (“supervisor” vs. “supervisor with routing”), proving they're distinct layers you can combine.

The three roles

Every vendor describes the same hub-and-spoke shape, with different names. See the Vocabulary tab for the full six-vendor map.

Role 1 · the coordinator

Orchestrator / Supervisor / Manager / Coordinator / Lead agent

The decision-maker at the top. Receives the goal, decides how to break it up and who handles each piece, delegates, and synthesizes results. Owns the outcome, does little domain work itself.

A supervisor is a central agent that “controls all communication flow and task delegation, making decisions about which agent to invoke based on the current context and task requirements.” LangGraph, langgraph-supervisor · verbatim

Thinks about

  • “How do I decompose this?”
  • “Which worker gets which piece?”
  • “Do I have enough, or spawn more?”

Superpower / risk

  • ✅ Flexible, dynamic decomposition
  • ⚠️ Bottleneck & single point of failure
  • ⚠️ Re-encodes worker output — a lossy “telephone” step (see The Debate)
Role 2 · the process

Orchestration — centralized vs. decentralized

“Orchestration” is the flow: which agents run, in what order, and how the next step is decided.

“There are two main ways to orchestrate agents: 1. Allowing the LLM to make decisions… 2. Orchestrating via code.” OpenAI, Agents SDK — Orchestration · verbatim

Manager pattern (centralized)

  • A central manager coordinates specialists through tool calls (agents-as-tools).
  • One agent keeps control and access to the user.

Decentralized pattern (peer)

  • Agents hand off control to a peer that takes over.
  • Microsoft implements this as “a mesh topology where agents are connected directly without an orchestrator.”
🔀
Handoff ≠ delegation. Google states this most cleanly of anyone:
“Agent-as-a-Tool: Agent B's answer is passed back to Agent A… Agent A retains control.”
“Sub-agent: responsibility is completely transferred to Agent B. Agent A is effectively out of the loop.”
Role 3 · the specialist

Sub-agent / Worker / Participant / Domain agent

The specialist that does the work. Narrow scope, focused sub-task, focused result. In Anthropic's research system the lead agent spawns typically 3–5 subagents in parallel.

✅
Myth to drop: “a sub-agent is a smaller/weaker agent.” It names a role in a hierarchy — delegated-to, scoped, reports up — not a size class. Anthropic ran subagents on Sonnet with an Opus lead, but that's an implementation choice.
🧠
The 2026 reframe: sub-agents are now understood primarily as a context-management primitive, not a parallelism one. See the section below.

Context engineering — the frame that reorganized everything

Since late 2025 the dominant lens is context as a finite attention budget, not a container you fill.

“as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases… Context, therefore, must be treated as a finite resource with diminishing marginal returns. Like humans, who have limited working memory capacity, LLMs have an ‘attention budget’…” Anthropic, Effective context engineering for AI agents (Sep 2025) · full text

Goal: “finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome.” Three named long-horizon techniques:

1 · Compaction

  • Summarize a near-full context and reinitialize with the summary.
  • “overly aggressive compaction can result in the loss of subtle but critical context whose importance only becomes apparent later.”

2 · Structured note-taking

  • The agent “regularly writes notes persisted to memory outside of the context window.”

3 · Sub-agent architectures

  • “specialized sub-agents can handle focused tasks with clean context windows.”
  • Each “might explore extensively, using tens of thousands of tokens… but returns only a condensed, distilled summary (often 1,000-2,000 tokens).”

The corollary everyone now states

  • A sub-agent must return a distilled answer, never raw data.
  • If it dumps its transcript back, you paid the coordination cost and got zero context savings.
💡
This is why sub-agents survive the skeptic critique. Their justification shifted from “do work in parallel” to “keep exploration out of the parent's context window.” Parallel speedup became a side effect.

The honest cost/benefit

“agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats. For economic viability, multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance.”

“Multi-agent systems work mainly because they help spend enough tokens to solve the problem… token usage by itself explains 80% of the variance, with the number of tool calls and the model choice as the two other explanatory factors.” Anthropic, How we built our multi-agent research system (Jun 2025) · full text
📊
Read that second quote carefully. Anthropic's headline “multi-agent beat single-agent by 90.2%” was not token-matched. By their own regression, most of the gain is explained by spending more tokens. Treat any “multi-agent wins” claim as unfalsified until you know the token budget.

When multi-agent wins

  • Heavy parallelization
  • Information exceeding one context window
  • Many complex tools; breadth-first research

When it doesn't — Anthropic's own words

  • “some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit”
  • “most coding tasks involve fewer truly parallelizable tasks than research”

Traps this table fixes

❌ “Anthropic calls it a supervisor”

  • They don't. Anthropic says orchestrator and lead agent. “Supervisor” is LangGraph & AWS.

❌ “Microsoft says supervisor”

  • Essentially no. Microsoft's word is manager. “Supervisor” appears only in their reference-architecture repo, and there it's a mid-tier grouping — see the Layering tab.

❌ “Google says orchestrator”

  • Google's coordinator word is Coordinator. It reserves “orchestrator” for the deterministic workflow agents — a genuinely different thing.

❌ “Handoff is a standard term”

  • OpenAI's handoff = a peer taking over. LangGraph uses it for any transfer including supervisor→worker. Same word, different scope.

❌ “Orchestration = orchestrator agent”

  • Anthropic uses “orchestrated” for hardcoded workflows. Orchestration can be pure code; an orchestrator agent decides dynamically.

❌ “Hierarchical is its own species”

  • LangGraph defines it as “a supervisor of supervisors” — a generalization of the supervisor pattern.

Can you have a supervisor and an orchestrator in one flow?

A question that trips up almost everyone, because the honest answer is “yes, but not for the reason you think.”

The short answer

Yes — but not as two different kinds of agent. As two layers, or two functions.

Since “orchestrator,” “supervisor,” “manager,” and “coordinator” are vendor synonyms for one role, designing a flow with “a supervisor agent” and “an orchestrator agent” as natively distinct types just picks two synonyms and assigns them different jobs by fiat. Nothing in the primary sources supports that split, and readers from a different vendor background will misread your diagram.

But there are three genuinely documented ways to have two coordinating nodes in one flow:

The three legitimate splits

Split by…Who documents itThe two roles
Altitude LangGraph; Microsoft reference architecture A top coordinator plans; a mid-tier coordinator abstracts a domain so the top isn't routing among dozens of leaves.
Determinism Google ADK; Microsoft Magentic One node decides dynamically (LLM); the other runs fixed control flow (code).
Function AWS; Anthropic One classifies and routes; the other decomposes and synthesizes.
Split 1 · by altitude

“A supervisor of supervisors”

“Hierarchical: you can define a multi-agent system with a supervisor of supervisors. This is a generalization of the supervisor architecture and allows for more complex control flows.” LangGraph, Multi-agent Systems · verbatim

Microsoft's reference architecture is the one place a vendor uses both words as distinct tiers — and it's exactly this shape:

“Orchestrator agent… acts as the central coordinator within the multi-agent workflow. It receives incoming requests… and formulates a high-level plan composed of individual tasks.”

“Introduce agent supervisors as the architecture scales across domains — these components help manage and abstract groups of related agents.” … “Use hierarchical organization (e.g., supervisor → agent group).” Microsoft, multi-agent-reference-architecture · verbatim
✅
So orchestrator agent → agent supervisors → specialized agents is a documented topology. The supervisor tier earns its place by abstracting a domain, not by relaying.
Split 2 · by determinism

LLM coordinator + deterministic orchestrator

Google is the clearest case: it uses “Coordinator” and “orchestrator” for different things.

Coordinator — “A central LlmAgent (Coordinator) manages several specialized sub_agents… Route incoming requests to the appropriate specialist agent.”

Workflow agents as orchestrators — “ADK includes specialized agents… that don't perform tasks themselves but orchestrate the execution flow of their sub_agents”: SequentialAgent, ParallelAgent, LoopAgent. Google, ADK — Coordinator and dispatcher / Workflow agents · verbatim

Microsoft's Magentic splits the same way inside one pattern — a manager (LLM judgment) and an orchestrator executor (runtime routing):

StandardMagenticManager — “Calls the underlying chat model to gather facts, build plans, evaluate progress, and synthesize the final answer.”
MagenticOrchestratorExecutor — “Implements the coordination loop — routing manager instructions to participants, collecting agent responses, and deciding when to reset or finish.” Microsoft, Magentic orchestration · verbatim
🔎
This maps onto Anthropic's workflow-vs-agent split: the coordinator is the dynamic part; the workflow agent is the predefined code path part.
Split 3 · by function

Router feeding an orchestrator

AWS ships this as two product modes: plain supervisor mode vs. supervisor with routing, where simple requests go straight to a specialist and complex ones fall back to full orchestration. Anthropic likewise treats routing and orchestrator-workers as separate patterns. So triage/router → orchestrator → sub-agents is real, and the two nodes do measurably different work.

⚖️ The test: does the layer transform, or just relay?

A coordination layer that mostly forwards is actively harmful, not merely wasteful. LangChain benchmarked this:

“the swarm architecture slightly outperforms supervisor architecture across the board… the drop in performance arises due to the ‘translation’ the supervisor is doing… If you've ever played a game of ‘telephone,’ you're already familiar with this problem!” LangChain, Benchmarking Multi-Agent Architectures (Jun 2025) · full text

So a layer earns its place only if it does at least one of:

✅ Decomposition

  • Splits work that wasn't split before.

✅ Synthesis

  • Merges results into something new.

✅ Verification

  • Judges with independent context.

❌ Relaying

  • Picks a child and forwards. This is the telephone game — pure loss.
💸
And every hop costs a full LLM round-trip. With multi-agent already at ~15× chat token usage, a relay layer is expensive and lossy.

📐 Practical naming guidance

Do

  • Name nodes by function or scope: TriageRouter → ResearchOrchestrator → sub-agents.
  • State which vendor's vocabulary you're using.
  • Justify each layer against the transform-vs-relay test.

Don't

  • Write Supervisor → Orchestrator and expect it to be understood — every reader will guess a different meaning.
  • Add a tier just because the diagram looks tidier.

The live debate

Vendor docs tell you what's possible. This is what practitioners have argued about — and what they've changed their minds on.

June 2025: the clash

Two influential posts landed a day apart with opposite titles.

The skeptic

“Don't Build Multi-Agents”

Walden Yan, Cognition · Jun 2025

Principle 1: “Share context, and share full agent traces, not just individual messages”
Principle 2: “Actions carry implicit decisions, and conflicting decisions carry bad results”

The subtle part most summaries miss: copying the original prompt to each subagent doesn't fix it. Two subagents building a bird and a background “end up with completely different visual styles… based on conflicting assumptions not prescribed upfront.” Context is generated by action, so sharing the prompt isn't sharing the context.

Prescription: “just use a single-threaded linear agent,” with a dedicated compression model when context overflows.

The advocate

“How we built our multi-agent research system”

Anthropic · Jun 2025

Orchestrator-worker in production: an Opus 4 lead agent spawning parallel Sonnet 4 subagents, “outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval.”

But they independently hit Yan's failure mode: vague instructions meant “subagents misinterpreted the task or performed the exact same searches as other agents.”

And they concede his home turf: domains “that require all agents to share the same context or involve many dependencies… are not a good fit.”

The reconciliation — read vs. write

Four days later Harrison Chase pointed out the two posts mostly agree:

“Despite their opposing titles, I would argue they actually have a lot in common… 1. Context engineering is crucial 2. Multi-agent systems that primarily ‘read’ are easier than those that ‘write’”

“The key insight is that read actions are inherently more parallelizable than write actions. When you attempt to parallelize writing, you face the dual challenge of effectively communicating context between agents and then merging their outputs coherently.” Harrison Chase, LangChain, How and when to build multi-agent systems · full text

And the observation that dissolves the apparent conflict — Anthropic's system already obeyed single-threaded writes:

“the multi-agent architecture primarily handles the research (reading) component. The actual writing — synthesizing findings into a coherent report — is deliberately handled by a single main agent in one unified call.” Same source · full text

⭐ April 2026: the skeptic revises

The most important and least-known update: Cognition publicly revised its own famous position.

“10 months ago, I wrote Don't Build Multi-Agents… A lot has changed since then.”

“we've found a narrower class of patterns that do [work]: setups where multiple agents contribute intelligence to a task while writes stay single-threaded.”

“multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions.” Walden Yan, Cognition, Multi-Agents: What's Actually Working (Apr 2026) · full text

And a genuine reversal of Principle 1 — for verification, sharing context is harmful:

“we found this technique to work best when the coding and review agents do not share any context beforehand.”

“the reviewer is forced to reason backward from the implementation without the spec… having a clean context makes the agent smarter because of the math of attention. The dedicated review agent gets to skip this extraneous context, only look at the diff, and re-discover any context it needs.” Same source · full text

Reported result: Devin Review catches an average of 2 bugs per PR on Devin-written PRs, ~58% severe.

Still skeptical of swarms, though: “the unstructured-swarm approach, arbitrary networks of agents negotiating with each other, is mostly a distraction. The practical shape is map-reduce-and-manage.”

🔑 The reconciliation worth memorizing

The 2025 argument was largely an equivocation on the word context. Untangled:

Decision context — SHARE it

  • Intent, constraints, prior choices, taste.
  • Must be continuous and single-threaded.
  • Fragmenting it is what makes swarms fragile.

Working context — ISOLATE it

  • Search results, file reads, failed attempts, tool spam.
  • Should be discarded after distillation.
  • Accumulating it causes context rot.
🎯
Every pattern that survived to 2026 — read-only sub-agents, clean-context reviewers, planner/worker/judge, map-reduce-and-manage — isolates working context while keeping decision context single-threaded. That's the whole synthesis in one sentence.

Where experts still genuinely disagree

1 · Does a verifiable oracle dissolve coordination?

  • Swarm side: if the build passes, the artifact is the shared context. Anthropic built a C compiler with 16 parallel Claudes coordinating via lock files and git merge conflicts; Cursor ran hundreds of agents for weeks.
  • Cognition's answer: those demos “all share a property most real software doesn't: a simple, verifiable success criterion.”
  • Not resolvable in the abstract — it's a question about your domain.

2 · Supervisor or handoff?

  • LangChain's benchmark found swarm handoffs beat supervisors (the telephone problem).
  • Cognition calls arbitrary agent networks “mostly a distraction.”
  • Both right for different workloads: handoff wins when a sub-agent can own the user interaction; supervisor wins when results must be synthesized.

3 · Architecture, or just token spend?

  • Token usage explains ~80% of variance; multi-agent burns ~15×.
  • A 2026 paper (“A Strong Single Agent Baseline”) finds a single agent matches homogeneous multi-agent workflows across 7 benchmarks, more cheaply.
  • Nobody has cleanly rebutted the token-matching objection.

4 · Flat or hierarchical?

  • Cursor started flat peer-to-peer and it failed — lock bottlenecks, idle waiting, and equal-status agents becoming risk-averse with nobody owning hard problems.
  • They moved to hierarchical planner → worker → judge with one-way communication and fresh starts each cycle.

Where they now agree

Architecture

  • Single-threaded writes. Parallelism belongs on the read/explore side.
  • Sub-agents are context management, not parallelism.
  • A sub-agent returns a distilled answer, never raw data.
  • Don't start multi-agent. Universal.

Verification & ops

  • Fresh context beats accumulated context for judging — converged on independently by Anthropic and Cognition.
  • Verification must be structural, not requested: “Asking nicely in the prompt doesn't reliably stop this.”
  • Durable execution, checkpointing, resumability are table stakes.
  • Most failures are organizational, not model-quality.
“Default-FAIL contract. Every criterion starts false; the agent can't mark it passing without opening evidence first.”
“Fresh-context evaluator. A separate agent with no Write/Edit tools grades the work from a context window that never saw the build.”
“Agent-maintained handoff. The agent writes its own progress notes and commits to git so the next session picks up cleanly.” Anthropic, harness design for long-running agents · verified repo

The meta-lesson almost nobody writes down: the right amount of scaffolding shrinks with each model release. Blueprints — what these actually look like in JSON

One blueprint per simulator trace. Each is a vendor-neutral agent definition you can adapt, with the system prompts written to encode the lessons from the Debate tab — not generic role-play.

How to read these

The schema is neutral

  • role — coordinator · worker · judge
  • sub_agents — delegated-to children (Google ADK's actual param name)
  • handoffs — peers that can take over the turn (OpenAI semantics)
  • output_contract — what the agent must return, and how big
  • context_policy — what this agent may and may not see

Mapping to your SDK

  • OpenAI: sub_agents → agents-as-tools; handoffs → handoffs=[...]
  • Google ADK: sub_agents maps 1:1; handoff = transfer_to_agent()
  • LangGraph: coordinator → supervisor node; handoff → Command(goto=...)
  • Microsoft: coordinator → Magentic manager; handoff → Handoff orchestration
🎯
The thing to steal from these is the output_contract and context_policy. Most published examples get the topology right and the contracts wrong — which is exactly where multi-agent systems fail in production.
Blueprint 1 · orchestrator-workers

Research report dynamic decomposition

The lead agent decides subtasks at runtime, fans out to read-only workers, then writes the output itself in one pass.

research-orchestrator.json
{
  "pattern": "orchestrator-workers",
  "writes": "single-threaded",
  "agents": [
    {
      "name": "lead_researcher",
      "role": "coordinator",
      "model": "large",
      "system_prompt": [
        "You are the lead agent for a research task. You do not run searches yourself.",
        "",
        "DECOMPOSE AT RUNTIME. Read the query and decide what the subtasks are.",
        "Do not apply a fixed template. A question about market sizing and a",
        "question about a technical standard need different decompositions.",
        "",
        "DELEGATION CONTRACT. Every task you send a subagent MUST specify:",
        "  1. objective        - the single question this subagent answers",
        "  2. scope            - sources or angles to cover",
        "  3. exclusions       - what OTHER subagents are covering, so you do not overlap",
        "  4. output_format    - the exact shape you want back",
        "Never send an instruction shorter than two sentences. Vague instructions",
        "cause subagents to duplicate each other's searches or miss the target.",
        "",
        "SPAWN 3-5 subagents for a broad query. Fewer for a narrow one.",
        "Subagents run in parallel and cannot see each other. Assume zero shared state.",
        "",
        "SYNTHESIZE YOURSELF. When findings return, you write the final report in a",
        "single pass. Do NOT delegate writing. Parallel writing produces inconsistent",
        "voice and conflicting assumptions.",
        "",
        "STOP when every objective has a grounded answer, or you have spawned two",
        "rounds without new information."
      ],
      "sub_agents": ["research_subagent", "analysis_subagent"],
      "output_contract": {
        "type": "markdown_report",
        "must_include": ["executive_summary", "findings_with_citations", "open_questions"]
      }
    },
    {
      "name": "research_subagent",
      "role": "worker",
      "model": "fast",
      "system_prompt": [
        "You are a research subagent with a CLEAN context window.",
        "You can see only the task given to you. You cannot see the user's original",
        "phrasing, the overall plan, or what other subagents are doing.",
        "If the task seems ambiguous, state your interpretation in your output",
        "rather than guessing silently.",
        "",
        "RETURN CONTRACT - this is the whole point of your existence:",
        "  - Return AT MOST 1500 tokens.",
        "  - Return findings, not transcripts. Never paste raw search results.",
        "  - Every claim carries a source URL.",
        "  - Mark confidence: verified | corroborated | speculative.",
        "You may internally read 40k+ tokens. None of it goes back to the lead agent.",
        "You are a context filter, not a pipe."
      ],
      "tools": ["web_search", "fetch_page"],
      "context_policy": { "inherits_parent_history": false },
      "output_contract": { "max_tokens": 1500, "format": "findings[]" }
    },
    {
      "name": "analysis_subagent",
      "role": "worker",
      "model": "large",
      "system_prompt": [
        "You receive structured findings from research subagents.",
        "Compute what is computable. Identify at most 3 themes.",
        "Flag contradictions between findings explicitly - do not silently pick one.",
        "Return AT MOST 1200 tokens of analysis. No prose padding."
      ],
      "context_policy": { "inherits_parent_history": false },
      "output_contract": { "max_tokens": 1200, "format": "themes[]" }
    }
  ]
}
1

2
“You are a context filter, not a pipe” enforces the 2026 reframe — a sub-agent that returns its transcript gives you the coordination cost with none of the context savings.
3
“Do NOT delegate writing” is the single-threaded-write rule. Anthropic's own research system did this deliberately.
Blueprint 2 · routing

Analytics router classify → one path

No decomposition, no synthesis. The router's whole job is to pick a lane and get out of the way.

      "routes": ["sql_agent", "docs_agent", "escalate_human"],
      "output_contract": {
        "format": "json",
        "schema": { "route": "string", "confidence": "number", "rationale": "string" }
      }
    },
    {
      "name": "sql_agent",
      "role": "worker",
      "model": "large",
      "system_prompt": [
        "You answer data questions against the orders warehouse.",
        "ALWAYS: show the SQL you ran, then the result, then a one-line plain answer.",
        "NEVER: guess a number. If the query returns empty, say so.",
        "Cap result sets at 100 rows; aggregate rather than dumping rows."
      ],
      "tools": ["run_sql", "describe_schema"],

1
“A router that answers is a router you can no longer reason about.” Routers that sometimes answer inline destroy your ability to trace and evaluate the system.
2
Structured route output makes the decision loggable and evaluable — you can measure routing accuracy separately from answer quality.
Blueprint 3 · parallelization (sectioning)

Competitor scan fixed split, in code

The split is known in advance, so it lives in code — not in an LLM's judgment. One worker prompt, parameterized N ways.

competitor-scan.json
{
  "pattern": "parallelization/sectioning",
  "distinction": "The split is hardcoded. If an LLM chose the split, this would be orchestrator-workers.",
  "fan_out": {
    "over": "competitors",
    "values": ["acme", "globex", "initech"],
    "worker": "pricing_scout",
    "join": "collect_all"
  },
  "agents": [
    {
      "name": "pricing_scout",
      "role": "worker",
      "model": "fast",
      "instances": 3,
      "system_prompt": [
        "You research the public pricing of exactly ONE company: {{competitor}}.",
        "",
        "You are one of several identical scouts running in parallel on different",
        "companies. You cannot see the others. Do not comment on other companies,",
        "do not compare, do not recommend. Comparison happens downstream.",
        "",
        "RETURN a pricing table only:",
        "  tier_name | monthly_usd | annual_usd | seat_minimum | notable_limits | source_url",
        "If a tier is 'contact sales', record it as null with a note. Do not estimate.",
        "MAX 800 tokens."
      ],
      "tools": ["web_search", "fetch_page"],
      "context_policy": { "inherits_parent_history": false, "sees_sibling_output": false },
      "output_contract": { "max_tokens": 800, "format": "pricing_rows[]" }
    },
    {
      "name": "comparison_writer",
      "role": "coordinator",
      "model": "large",
      "system_prompt": [
        "You receive N pricing tables collected in parallel.",
        "Write the comparison yourself in a single pass - this is a WRITE step",
        "and must not be parallelized.",
        "Normalize currencies and billing periods before comparing.",
        "Where a scout returned null, say 'not published' - never interpolate."
      ],
      "output_contract": { "format": "comparison_table + recommendation" }
    }
  ]
}
1
“Do not compare, do not recommend” keeps workers on reads. The moment a worker starts forming an opinion about the whole, you've created the conflicting-assumptions problem.
2
"instances": 3 with one prompt is the tell that this is sectioning, not orchestrator-workers. Identical workers, code-decided split.
Blueprint 4 · decentralized handoff

Support triage control transfer, not delegation

The receiving agent owns the conversation afterwards. Nothing reports back.

support-handoff.json
{
  "pattern": "decentralized/handoff",
  "semantics": "Control and conversation ownership transfer. The sender is out of the loop.",
  "agents": [
    {
      "name": "triage_agent",
      "role": "coordinator",
      "model": "fast",
      "system_prompt": [
        "You are the first responder. Identify intent, then hand off.",
        "",
        "You are NOT a manager. When you hand off, you are done - the receiving",
        "agent talks to the customer directly and will not report back to you.",
        "So transfer everything they need in the handoff payload.",
        "",
        "HANDOFF PAYLOAD must carry:",
        "  - customer_id and verified status",
        "  - the customer's goal in your own words",
        "  - anything already tried in this conversation",
        "  - what you have ALREADY promised the customer (critical - do not let",
        "    the next agent contradict you)",
        "",
        "Do not hand off more than twice. A third transfer means escalate to a human."
      ],
      "handoffs": ["billing_agent", "technical_agent", "human_queue"],
      "handoff_payload_schema": {
        "customer_id": "string",
        "verified": "boolean",
        "goal": "string",
        "already_tried": "string[]",
        "promises_made": "string[]"
      }
    },
    {
      "name": "billing_agent",
      "role": "worker",
      "owns_conversation_after_handoff": true,
      "model": "large",
      "system_prompt": [
        "You have taken over this conversation. You now own it end to end.",
        "",
        "Read promises_made FIRST and honor every one of them. The customer was",
        "told these things by us; contradicting them is worse than the original problem.",
        "",
        "You may issue refunds up to $200 without approval. Above that, or for",
        "accounts flagged 'enterprise', hand off to human_queue with a summary.",
        "Never mention that you are a different agent than the one before."
      ],
      "tools": ["lookup_charge", "issue_refund", "escalate"],
      "handoffs": ["human_queue"]
    }
  ]
}
1
promises_made is the single most-skipped field in real handoff systems, and the one that generates the worst customer experiences. Handoffs lose implicit commitments unless you make them explicit.
2
“Do not hand off more than twice” — handoff loops are a documented failure mode. Bound them structurally.
3
LangChain's benchmark found handoffs beat supervisors here, because the specialist speaks to the user directly — no lossy re-encoding.
Blueprint 5 · fresh-context judge ⭐

Code review the 2026 pattern

The highest-leverage blueprint here. Note that context_policy is mostly a list of things the judge is forbidden to see.

fresh-context-judge.json
{
  "pattern": "evaluator/fresh-context-judge",
  "principle": "The builder should not grade its own work, and the grader should not inherit the builder's context.",
  "agents": [
    {
      "name": "review_agent",
      "role": "judge",
      "model": "large",
      "context_policy": {
        "inherits_parent_history": false,
        "receives": ["diff", "repo_read_access", "test_command"],
        "must_not_receive": [
          "original_spec",
          "builder_conversation",
          "builder_planning_notes",
          "builder_self_assessment"
        ],
        "rationale": "Ignorance of the spec is the feature. Forced to reason backward from the implementation, the judge re-derives intent and catches where code and intent diverge."
      },
      "tools": ["read_file", "run_tests", "git_log"],
      "forbidden_tools": ["write_file", "edit_file", "commit"],
      "system_prompt": [
        "You are reviewing a code change. You have NOT seen the specification,",
        "the plan, or the conversation that produced it. This is intentional.",
        "",
        "STEP 1 - Reconstruct intent. From the diff alone, state what you believe",
        "this change is trying to do. Write it down before evaluating anything.",
        "",
        "STEP 2 - Evaluate against the DEFAULT-FAIL rubric below. Every criterion",
        "starts as FAIL. You may only mark PASS after citing specific evidence:",
        "a file and line, or command output you actually ran. A criterion you did",
        "not check stays FAIL. Do not mark PASS because something looks fine.",
        "",
        "STEP 3 - Report. For each finding give severity, location, and the concrete",
        "failure scenario (inputs to wrong behavior). No stylistic nitpicks.",
        "",
        "You cannot edit anything. Do not propose a full rewrite - report defects."
      ],
      "rubric": [
        { "id": "tests_pass",      "default": "FAIL", "evidence_required": "test command output" },
        { "id": "no_regressions",  "default": "FAIL", "evidence_required": "file:line of preserved behavior" },
        { "id": "errors_handled",  "default": "FAIL", "evidence_required": "file:line of error path" },
        { "id": "no_secrets",      "default": "FAIL", "evidence_required": "grep output" },
        { "id": "intent_matches",  "default": "FAIL", "evidence_required": "reconstructed intent vs diff" }
      ],
      "output_contract": {
        "format": "json",
        "schema": {
          "reconstructed_intent": "string",
          "rubric_results": "array",
          "findings": "array of { severity, file, line, failure_scenario }"
        }
      }
    }
  ]
}
1
Default-FAIL with evidence gates is Anthropic's harness pattern verbatim: “Every criterion starts false; the agent can't mark it passing without opening evidence first.” Because “asking nicely in the prompt doesn't reliably stop this.”
2
must_not_receive inverts the usual advice on purpose. Cognition: “we found this technique to work best when the coding and review agents do not share any context beforehand.”
3
forbidden_tools makes “judge cannot become builder” structural rather than instructional. Anthropic's evaluator has no Write/Edit tools at all.
Blueprint 6 · ⚠️ the anti-pattern

Parallel writers annotated failure

This looks reasonable and is the most common multi-agent mistake. Annotations mark where it breaks.

DO-NOT-SHIP.json
{
  "pattern": "parallel-writers",
  "status": "ANTI-PATTERN - shown so you can recognize it",
  "agents": [
    {
      "name": "coordinator",
      "role": "coordinator",
      "system_prompt": [
        "Split the app build across three agents and merge their work.",
        "Pass each agent the full original user request so they share context."
      ],
      "_flaw_1": "Sharing the PROMPT is not sharing the CONTEXT. Context is generated by action - each agent's choices are invisible to the others.",
      "sub_agents": ["sprite_agent", "background_agent", "physics_agent"]
    },
    {
      "name": "sprite_agent",
      "role": "worker",
      "writes_to": ["src/sprites/"],
      "system_prompt": ["Build the player sprite. Match the game's visual style."],
      "_flaw_2": "'Match the visual style' is unresolvable - no style has been decided yet, and this agent cannot see what the others chose. It will pick one reasonably and be wrong."
    },
    {
      "name": "background_agent",
      "role": "worker",
      "writes_to": ["src/background/"],
      "system_prompt": ["Build the background art. Match the game's visual style."],
      "_flaw_3": "Same instruction, different reasonable answer. One agent produces cartoon, the other photorealistic. Both followed orders."
    },
    {
      "name": "physics_agent",
      "role": "worker",
      "writes_to": ["src/physics/"],
      "system_prompt": ["Tune collision and gravity for the player sprite."],
      "_flaw_4": "Depends on a sprite that does not exist yet. It will assume dimensions, and the assumption will be wrong."
    }
  ],
  "_why_it_fails": "Actions carry implicit decisions, and conflicting decisions carry bad results. Three agents made three defensible choices that cannot be merged.",
  "_the_fix": {
    "option_a": "Single-threaded write: one agent builds all three, optionally consulting read-only advisors.",
    "option_b": "Decide the shared decisions UP FRONT (style guide, sprite dimensions) and freeze them into every prompt before fanning out.",
    "option_c": "Add a mechanical oracle - if a build/test can adjudicate correctness, parallel writes become viable (this is how the parallel-Claudes C compiler worked)."
  }
}
1
Option B is the underrated fix. Parallel writes fail on undecided shared decisions. Decide them first, freeze them into every prompt, and much of the fragility disappears.
2
Option C is the live debate. Cursor and Anthropic have run large parallel-writer systems successfully — but Cognition's counter is that those tasks “share a property most real software doesn't: a simple, verifiable success criterion.”

🧱 Prompt building blocks — a few variants per role

Reusable fragments. Pick the variant that matches how much autonomy you actually want.

coordinator-variants.txt
=== A. Tight coordinator (predictable, cheaper) ===
You decompose the request into at most 4 subtasks drawn ONLY from this list:
{search, summarize, compute, draft}. If the request needs something outside
this list, say so instead of improvising. Delegate, then synthesize yourself.

=== B. Open coordinator (flexible, costlier) ===
You decide what the subtasks are - there is no fixed menu. State your plan
before delegating, and revise it if returning results contradict it.
Prefer 3-5 subagents. Every task you send must name what it EXCLUDES so
parallel subagents do not overlap.

=== C. Budgeted coordinator (production) ===
You have a budget of 8 subagent calls and 120k total tokens for this task.
Announce your plan and its projected cost before spending anything.
If a plan would exceed budget, cut scope and say what you cut.
When 80% of budget is consumed, stop delegating and synthesize what you have.
Multi-agent runs cost roughly 15x a single chat turn - spend deliberately.
worker-variants.txt
=== A. Read-only scout (safest, most parallelizable) ===
You investigate and report. You have no write tools and must not propose
edits. Return at most 1200 tokens: findings only, each with a source.
You are a context filter - your exploration does not travel back upstream.

=== B. Scoped writer (one owner per surface) ===
You own exactly these paths: {paths}. You may not read or write outside them.
If your task appears to require touching another path, STOP and report the
dependency instead of reaching across. Another agent owns that surface.

=== C. Advisor (contributes intelligence, not actions) ===
You are consulted for judgment, not execution. Return a recommendation with
reasoning and an explicit confidence level. You do not act, and the agent
that called you is free to overrule you. If you are less than 60% confident,
say so plainly rather than hedging in prose.
judge-variants.txt
=== A. Rubric judge (default-FAIL) ===
Every criterion starts FAIL. Mark PASS only after citing evidence you
personally obtained - a file:line or command output. Unchecked stays FAIL.

=== B. Adversarial refuter (for high-stakes claims) ===
Your job is to REFUTE the claim below, not to evaluate it fairly.
Find the input that breaks it. If after genuine effort you cannot construct
a failing case, say so - that is a meaningful result. Default to 'refuted'
when uncertain; a false pass is far more expensive than a false alarm.

=== C. Fresh-eyes reviewer (no spec) ===
You have not seen the requirements. First reconstruct, from the artifact
alone, what it is trying to do. Then report where the artifact and your
reconstructed intent diverge - those gaps are usually the real bugs.
💡
Pairing guide: Tight coordinator + read-only scouts = cheap and predictable. Open coordinator + scoped writers = flexible but needs strong ownership boundaries. Any writer at all = add a judge, ideally variant C.
